# Поддержка старых версий Bedrock (1.21.x → 26.65): что реально возможно

Короткий ответ: **«любая версия Bedrock с 1.21 до 26.65, без ошибок и без багов вообще» —
это не задача уровня настройки плагина.** Это отдельный проект масштабом в месяцы, и гарантии
«0 багов» не даёт никто, включая сам GeyserMC. Ниже — почему, с точными местами в коде,
и что можно сделать уже сегодня.

---

## 1. Что происходит с игроком на 1.21.144

Он отключается **до** игровой логики — на этапе `RequestNetworkSettings`, когда клиент сообщает
свой протокол.

`core/src/main/java/org/geysermc/geyser/network/bedrock/LoginPacketHandler.java` (`setCorrectCodec`):

```java
BedrockCodec packetCodec = GameProtocol.getBedrockCodec(protocolVersion);
if (packetCodec == null) {
    if (protocolVersion < GameProtocol.DEFAULT_BEDROCK_PROTOCOL) {
        session.disconnect(GeyserLocale.getLocaleStringLog("geyser.network.outdated.client", supportedVersions));
        return false;
    }
}
```

Сообщение игроку: `Outdated client! Please use 26.40-26.65`. В консоли Geyser:

```
[Geyser-Spigot] <ник> has disconnected from the Java server because of §rOutdated client! Please use 26.40-26.65
```

То есть это **не баг, не «нет текстуры» и не проблема маппингов** — Geyser сознательно
не пускает клиентов, для которых у него нет кодека. Официальная позиция в вики
(geysermc.org/wiki/geyser/supported-versions): *«Older Bedrock versions are not supported»* —
потому что Bedrock обновляется автоматически на всех платформах.

## 2. Почему «просто разрешить старые версии» не работает

Поддержка версии Bedrock — это не один флаг, а **шесть слоёв**, и все они должны совпасть:

| # | Слой | Где в коде | Состояние сейчас |
|---|---|---|---|
| 1 | **Кодек протокола** (сериализаторы всех пакетов этой версии) | `GameProtocol.register(...)` | 4 семейства: `v2168_hotfix4` (26.40–26.44), `v2169` (26.45), `v2193` (26.50–26.52), `v2225` (26.60–26.65) |
| 2 | **Данные мира под версию**: палитра блоков, `runtime_item_states`, `creative_items`, `item_components`, биомы, идентификаторы сущностей | `core/src/main/resources/bedrock/*` | файлы есть только для `26_40`, `26_50`, `26_60` |
| 3 | **Палитры и конвертеры** (Java-блок/предмет → id конкретной Bedrock-версии) | `BlockRegistryPopulator:126-128`, `ItemRegistryPopulator:149-152` (`PaletteVersion(version, protocol, converter)`) | три палитры |
| 4 | **Гейты фич по протоколу** (какой пакет/поле можно отправлять этой версии) | `GameProtocol.is26_50orHigher` / `is26_60orHigher` | всего **7** использований во всём коде |
| 5 | **Даунгрейд контента**: чего у старого клиента нет — не отправлять или подменять (блоки, предметы, **сущности**, звуки, частицы, компоненты предметов) | трансляторы, `JavaLevelEventTranslator`, `JavaSoundTranslator`, `entity/factory` | рассчитано на текущее окно |
| 6 | **Resource pack**: манифест/формат пака, который примет старый клиент | `pack/**`, `registry/loader/ResourcePackLoader`, `GeyserIntegratedPack` | под текущие версии |

Именно слой 5 — причина ваших жалоб «кикает, если нет звука или текстуры (например, серные кубы)».
Когда сервер присылает сущность/звук/блок, которых в клиенте 1.21 нет, клиент получает неизвестный
id и рвёт соединение. Чтобы этого не было, для каждой поддерживаемой версии нужна **карта
«новое → ближайший старый аналог или ничего»**, и она должна покрывать все типы контента.

## 3. Масштаб: 1.21.x → 26.65 — это не «несколько версий»

- Между 1.21.x и 26.65 — **десятки протокольных версий** и примерно два года контента
  (новые блоки, предметы, мобы, звуки, механики, изменения формата паков).
- Сейчас Geyser держит окно **в 4 кодек-семейства** — и это при 340+ открытых issue.
  Каждое добавленное семейство умножает матрицу тестирования: кодек × данные мира × палитры ×
  контент-даунгрейд × паки × платформа (Spigot / Velocity / Fabric / Standalone…).
- Исторически окно Geyser было шире (несколько релизов подряд), но и тогда речь шла о
  **последних** версиях, а не о двухлетнем хвосте.

**Вывод:** «все версии с 1.21» — это по объёму работа, сопоставимая с отдельным проектом
(условно: 3–6 месяцев для команды из 2–3 человек, знакомых с Bedrock-протоколом), при этом
результат всё равно будет «работает в большинстве случаев», а не «0 багов».

## 4. Почему «вообще без багов» — недостижимо

Это не пессимизм, а свойство задачи: вы переводите между двумя разными играми, у которых
разные модели мира, инвентаря, боёвки и анимаций. Даже для 4 поддерживаемых версий Geyser
имеет сотни известных дефектов (движение/античиты, отдельные entity flags, часть инвентарных
транзакций). Чем шире окно версий, тем больше комбинаций «старый клиент × новый контент»,
и каждая — потенциальный баг. Реалистичная цель: **«не кикает и не крашит»** — да, этого можно
добиться фильтрацией контента; **«идеально играется»** — нет.

## 5. Что делать прямо сейчас (решает 95% жалоб)

1. **Обновить Geyser до актуального билда** (сейчас `2.12.1+`, поддерживает 26.40–26.65)
   и **Floodgate**, если используете. Обновлять нужно *и* Geyser, *и* Floodgate.
2. **Включить RakNet рядом с NetherNet.** В свежих версиях транспорт по умолчанию —
   только NetherNet (новый способ подключения), а старые клиенты умеют **только RakNet**:
   ```yaml
   bedrock:
     transport: both      # nethernet | both
     port: 19132          # UDP, NetherNet
     raknet-port: 19132   # UDP, RakNet (не должен совпадать с webrtc-port)
     webrtc-port: 19133   # UDP, WebRTC/NetherNet
   ```
   Если у вас было `transport: nethernet` — часть игроков может не подключаться вообще,
   независимо от версии.
3. **Не форсить паки** (убирает кики «не удалось загрузить ресурспак»):
   ```yaml
   gameplay:
     force-resource-packs: false
     enable-integrated-pack: false   # если нет своих паков
   ```
4. **Объяснить игрокам про версию.** На Android/iOS/Windows/консолях Bedrock обновляется сам;
   клиент 1.21.144 — это либо необновлённое устройство, либо сторонняя сборка APK.
   Пока клиент старше 26.40, Geyser его не пустит, и никакая настройка это не изменит.

Чек-лист для консоли:
- `Outdated client!` → версия клиента вне окна Geyser (обновить клиент или Geyser).
- `Outdated server!` → Geyser старее клиента (обновить Geyser).
- `Unable to connect to world` без сообщения → чаще всего порт/транспорт (`transport`, UDP-порты, firewall).

## 6. Варианты, если старые версии нужны по-настоящему

| Вариант | Что делается | Срок | Риск |
|---|---|---|---|
| **A. Апстрим + дисциплина обновлений** | Всегда актуальный Geyser, `transport: both`, паки не форсить, игрокам — обновить клиент | 0 | 0 |
| **B. Форк с расширением окна на 1–2 семейства вниз** | Добавить кодек + данные мира + палитру + конвертер + гейты + тесты для конкретных версий (например 26.30–26.40) | 2–6 недель на семейство | средний, но управляемый |
| **C. Полный диапазон 1.21 → 26.65** | Всё выше × десятки версий + массовый контент-даунгрейд (сущности/звуки/частицы/компоненты) + версии паков | месяцы, команда | высокий, «0 багов» недостижимо |

Промежуточных «волшебных» вариантов нет: публичного прокси, который понижает **протокол Bedrock**
(аналог ViaVersion, но для Bedrock-клиентов), не существует — есть только обратное направление
(ViaBedrock: Java-клиент → Bedrock-сервер).

### Что входит в этап 1 (вариант B), если делаем форк

1. Зафиксировать базу: форк апстрима на конкретном коммите + submodule'ы `mappings`, `languages`.
2. Добавить `PaletteVersion` + данные `bedrock/26_30/*` (палитра, runtime items, creative items,
   item components) — генерация из `CloudburstMC/Data` и `GeyserMC/mappings`.
3. Зарегистрировать кодек(и) в `GameProtocol`, расширить гейты `is26_xx_orHigher`.
4. Контент-гард: фильтр исходящих `AddEntity`/`LevelSoundEvent`/`LevelEvent`/`SetEntityData`
   по «знает ли клиент этот id» (таблица возможностей по протоколу) — это и убирает кики
   из-за «серных кубов».
5. Прогнать матрицу: старый клиент × новый сервер, чанки, инвентарь, паки, сущности.
6. Собрать артефакты (jar) в CI.

## 7. Почему в этом чате нет готового .jar

Это ограничение моей среды, а не отговорка — проверено:

- в песочнице **нет JDK** (`java: command not found`), поэтому компиляция невозможна в принципе;
- доступ к Maven-репозиториям, откуда Geyser тянет зависимости, **закрыт**
  (`repo.opencollab.dev` и `repo1.maven.org` не отвечают — код `000`), без них `./gradlew build`
  не соберётся даже при наличии JDK;
- официальные сборки с `download.geysermc.org` из песочницы **недоступны** (тоже `000`),
  а на GitHub Releases у GeyserMC релизов нет (только CI-артефакты и Maven).

Поэтому единственные честные пути получить jar:
1. **Скачать официальный билд** с <https://geysermc.org/download> (Spigot/Paper) — 1 минута,
   поддерживает 26.40–26.65;
2. **Собрать форк на GitHub Actions** — я могу подготовить workflow, который при пуше собирает
   `Geyser-Spigot.jar` и кладёт его в артефакты сборки (JDK и Maven там есть). Для варианта B
   это же и станет способом получать jar после каждого изменения.
