# Проект «Bedrock 1.21.x → 26.65»: план и этапы

Статус: **принят вариант C** (полный диапазон). Этот документ — рабочий план проекта,
а не обещание «сделаем за вечер». Ниже: архитектура, этапы с критериями приёмки, риски
и что уже сделано в репозитории.

## Зафиксированные решения

| Вопрос | Решение |
|---|---|
| Минимальная целевая версия Bedrock | **1.21.0** (полный хвост, включая 1.21.0–1.21.9) |
| Платформа | **Purpur** (форк Paper) → артефакт `Geyser-Spigot.jar`; Velocity/Fabric пока не нужны |
| Тестирование клиентов | вручную владельцем сервера (может скачать и запустить старую версию клиента) |

## 0. Что уже сделано (M0–M1)

- В репозиторий заложен **форк GeyserMC/Geyser** на коммите `cb04ea8af` (20.11.2026,
  `2.12.1-SNAPSHOT`), лицензия MIT сохранена (`LICENSE`).
- Подмодули `core/src/main/resources/mappings` (`GeyserMC/mappings`) и
  `core/src/main/resources/languages` (`GeyserMC/languages`) **вендорены как обычные каталоги**,
  чтобы сборка работала без `git submodule update`. Их происхождение и способ обновления — в
  `FORK.md`.
- Добавлен CI-workflow `.github/workflows/build-fork.yml`: собирает все 7 артефактов
  и складывает их в artifact `Geyser-jars` (там же `Geyser-Spigot.jar`).
  Это и есть способ получать готовый плагин после каждого изменения.

**M1 (каркас готов):** в ядро добавлен content guard — пакет `org.geysermc.geyser.compat`
(`ContentKind`, `LegacyContentManifest`, `ContentPolicy`, `ContentGuard`) и манифест
`compat/legacy-content.json`, подключённый в `UpstreamSession`. Пока манифест пустой, поведение
не меняется; после наполнения (M2) старый клиент перестаёт получать неизвестные сущности, звуки
и частицы вместо дисконнекта. Детали и ручной чек-лист — в `docs/m1-content-guard.md`,
автотесты — `ContentGuardTest`.

**Что это даёт:** уже сейчас можно собрать рабочий Geyser (поддержка 26.40–26.65) в CI
и начать накатывать изменения проекта, не имея JDK на машине.

## 1. Цель и критерий успеха

**Цель:** клиент любой версии Bedrock из диапазона 1.21.x … 26.65 подключается к серверу
и играет без дисконнектов и крашей.

**Главный принцип:** приоритет — *не рвать соединение*. Если контент клиенту неизвестен,
он **подменяется предсказуемым аналогом или не отправляется**, а не приводит к кику.
Это принципиально отличается от «идеального перевода», которого не будет.

**Критерии приёмки для каждого поддерживаемого семейства версий:**

| # | Проверка | Как проверяем |
|---|---|---|
| 1 | Вход | клиент получает `StartGame`, спавнится, не дисконнектится |
| 2 | Мир | чанки рендерятся, нет «дыр», нет краша на неизвестных блоках |
| 3 | Контент | сущности/звуки/частицы/предметы нового контента не вызывают обрыв |
| 4 | Инвентарь | открытие/закрытие, перемещение предметов, крафт — без «фантомных» предметов |
| 5 | Ресурспаки | пак применяется или корректно пропускается, без отказа подключения |
| 6 | Логи | в `latest.log` Geyser нет `disconnected ... because of`, нет stacktrace от трансляторов |
| 7 | Автотест | `LegacyClientCompatibilityTest` (headless, парсер-уровень) зелёный для матрицы protocol × образцы пакетов |

## 2. Архитектура: четыре новые подсистемы

### 2.1 `BedrockVersionRegistry` — единая модель возможностей клиента

Сейчас версии различаются точечными проверками (`GameProtocol.is26_50orHigher`,
`is26_60orHigher`, всего 7 мест). Для 40+ версий это не масштабируется.
Вводим перечисление возможностей вместо «магических» порогов:

```java
public enum Capability {
    CHUNK_FORMAT_V2, SUB_CHUNKS, ITEM_STACK_REQUEST_V2, DIALOGS, CAMERA_PRESETS,
    SULFUR_CUBE_ENTITY, NEW_SOUND_EVENTS, DATA_COMPONENTS_V3, BLOCK_PROPERTIES_MIRROR_X /* 26.60 */,
    RESOURCE_PACK_MANIFEST_V2, …
}
```

`session.has(Capability.X)` заменяет `GameProtocol.isXX_YYOrHigher(...)`.
Старый API оставляем как thin-wrapper, чтобы не ломать существующие call-site'ы.

### 2.2 `ContentFallbackLayer` — защита от неизвестного контента

Единая точка — `UpstreamSession.sendPacket` / `sendPacketImmediately`
(все исходящие Bedrock-пакеты проходят здесь, включая очередь `postStartGamePackets`).
Слой по типу пакета:

| Пакет | Что делаем |
|---|---|
| `StartGamePacket` (палитра блоков) | выкидываем/переименовываем блоки, которых нет в манифесте версии |
| `ItemComponentPacket`, `CreativeContentPacket` | то же для предметов и компонентов |
| `AddEntityPacket`, `AddPlayerPacket` | неизвестный тип → fallback-сущность (например `minecraft:pig`) или не спавним |
| `LevelSoundEventPacket`, `PlaySoundPacket`, `LevelEventPacket` | неизвестный id/имя → drop |
| `SetEntityDataPacket` | неизвестные метаданные → strip |
| `SpawnParticleEffectPacket` | неизвестная частица → drop |

Ограничение по производительности: проверки по `Object2BooleanOpenHashMap`/bitset'ам,
без аллокаций в горячем пути; включается только когда `protocolVersion < latest`.

### 2.3 Манифесты контента по версиям (данные)

Для фильтрации нужен ответ на вопрос «что знает клиент версии X». Источник — генератор
из курируемого датасета: имена блоков, предметов, сущностей, звуков, частиц по версиям
(ванильные списки Bedrock по релизам + наши `mappings/*.json` как канон для текущей версии).

Результат — `core/src/main/resources/compat/manifest_<ver>.json` +
загрузчик `LegacyManifestRegistry`. Генератор живёт в `tools/compat-gen/`
(запускается офлайн, результат коммитится — как `Blocks.java`).

### 2.4 `ProtocolBridge` — старые кодеки и дельты полей

- Регистрация кодеков старых версий в `GameProtocol` (библиотека `CloudburstMC/Protocol`
  хранит кодеки многих версий; `BedrockCompat.disconnectCompat` уже использует очень старые).
- Для версий, где различаются **поля** пакетов, — пофайловые сериализаторы/патчи в стиле
  `CodecProcessor` (там уже есть механизм замены сериализаторов).
- Регистрация «палитровых версий» (`PaletteVersion`) для каждой добавленной версии —
  с конвертером из канонической палитры.

## 4. Риски и как их снимаем

| Риск | Почему опасен | Мера |
|---|---|---|
| Старый клиент **крашится** вместо дисконнекта | в серверных логах этого не видно, жалобы приходят «не могу зайти» | тест на реальных клиентах каждой версии; smoke-набор версий в чек-листе релиза |
| Объём данных (манифесты на 40+ версий) | ручная работа не масштабируется | генератор + ревью диффов, как у `Blocks.java` |
| Апстрим уходит вперёд (26.66, 26.70…) | конфликты при rebase | политика: rebase раз в 2 недели, изменения локализованы в 4 подсистемах + реестрах |
| Производительность фильтра | горячий путь отправки пакетов | bitset'ы, включение только для старых протоколов, бенчмарк в CI |
| «0 багов» как ожидание | недостижимо технически | фиксируем контракт: «нет киков/крашей», визуальная деградация допустима и документируется |

## 6. Как проверить текущее состояние прямо сейчас

```bash
# локально (нужен JDK 21+ и доступ к maven-репозиториям Geyser)
./gradlew :bootstrap:spigot:build

# без локального JDK
# GitHub → Actions → «Build Geyser fork» → Run workflow → artifact Geyser-jars
```

Что даст этот jar: полностью рабочий Geyser для **26.40–26.65**. Старые клиенты
пока получают `Outdated client!` — их включит M2+.
